# 中继服务与多端同步：设计与落地计划

> 状态：服务端 MVP 已完成并已从客户端仓库分出，独立打包在 `D:/DL/serve.zip`（解压后为 `serve/`）；客户端接入已实施。
> 参考项目：`dsh-ee`（见文末「参考项目分析」）。

## 1. 目标

```
Android 客户端 ──┐
                ├─ HTTPS/HTTP ──> 中继服务 ──> api.deepseek.com
其他设备      ──┘                   │
                                    └─ SQLite（会话、账号、配置）
```

1. **转发全部官方接口**：对话（SSE 流）、文件、余额、搜索、文件解析、TTS/ASR 都从同一个出口走；
2. **多端会话同步**：任意设备改动，其他设备增量拉到；
3. **账号打通**：客户端用「用户名 + 密码」连中继，不必在每台设备存 API Key；
4. **自带 WebUI**：上游地址、服务端 Key、账号、令牌、数据统计；
5. 跨平台：Linux / Windows / macOS，HTTP 与 HTTPS 都支持。

## 2. 为什么是「中继」而不是「另一个后端」

客户端本来就是纯前端直连官方 API，加一层中继只解决三件直连解决不了的事：

| 问题 | 直连 | 中继 |
| --- | --- | --- |
| 每台设备都要存 Key | 是 | 只存中继令牌 |
| 聊天记录跨设备 | 各自 IndexedDB | 服务端一份，增量同步 |
| 换设备/重装 | 手动导出导入 | 登录即恢复 |

所以中继**不做业务**：不解析会话内容，不判断消息语义，只做转发与存取。「payload 对服务端是不透明 JSON」——这一点让后面加字段、加消息类型都不用改服务端。

## 3. 服务端 MVP（已完成）

服务端独立仓库（`serve.zip`，解压后 `serve/`），Node 22，零第三方依赖：

- `src/store.mjs`：SQLite（WAL），users / tokens / settings / sessions / changes 五张表；
- `src/server.mjs`：HTTP(S) 服务、鉴权、API 转发（含 SSE 透传）、同步接口；
- `src/webui.mjs`：单文件 WebUI（登录、概览、上游配置、账号、令牌、改密码）。

已实测：登录发令牌、会话推送、版本冲突 409、增量变更、代理转发（上游 401 原样透传）、路径白名单 403、WebUI 会话（无 Cookie 401）。

关键设计：

- **令牌只存哈希**（sha256），口令用 scrypt 加盐；
- **同步游标**：`changes` 表自增 `seq`，客户端记 `cursor` 增量拉；
- **每会话 rev**：写入必须带 `baseRev`，不符返回 409 + 最新内容，冲突交给客户端裁决；
- **tombstone 删除**，保证其他设备能感知删除；
- **代理白名单**：只放行 `/anthropic/`、`/chat/`、`/user/`、`/models`、`/v1/`、`/beta/`。

## 4. 客户端改造清单

### 4.1 数据模型

```
relayServers: [{ id, name, url, username, password?, token?, lastOk }]
```

- 密码只在「连接/登录」时用一次换 token，**不留明文**；token 存本地（后续可接系统密钥库）。
- 支持多个中继，界面上以 `name` 显示。

### 4.2 接口分流

设置 → 数据管理 →「接口设置」，四类各自选来源：

| 分类 | 说明（问号提示） | 可选 |
| --- | --- | --- |
| 对话调用 | messages / files / 余额 | 账户 / API / 中继名 |
| 网页搜索 | Search API 与 Fetch API | 同上 |
| 文件解析 | 文件解析与 OCR | 同上 |
| 语音服务 | TTS 与 ASR | 同上 |

实现：新增 `resolveRoute(kind)`，返回 `{ baseUrl, headers }`：

- `account`：现有 Harness 账号头；
- `apikey`：现有 `x-api-key` / `Bearer`；
- `relay:<id>`：`baseUrl = <relay>/api/v1/proxy`，头带中继 Bearer。

`client.ts` 里所有 `API_ORIGIN` / `ANTHROPIC_BASE_URL` 改为按 kind 取，转发层不用改业务代码。

### 4.3 设置页结构

数据管理（从上到下）：

```
API Key
账户余额        [充值]
API 余额
接口设置        >   （对话 / 搜索 / 解析 / 语音）
配置中继服务器   >
始终同步最新消息  [开关]
导入历史 / 导出历史 / 删除全部
```

- 「中继服务器」是二级页面：卡片样式、独立动画；**不再叠加第二层模糊**，因为设置本身已经有一层；
- 列表页：左侧名称，右侧编辑/删除；右上角 `+` 新增；删除二次确认；
- 详情页：名称、地址、用户名、密码、〔测试连接〕；测试走 `GET /api/v1/sync/state`。

### 4.4 用户信息源

通用设置 →「用户信息」，可选：`账号` 或某个中继。侧边栏头像/昵称按所选来源显示，避免多来源打架。

### 4.5 同步策略

- 打开「始终同步最新消息」：启动后静默拉取，只提示结果；
- 关闭：启动检测到差异时弹窗「是否从 xxx 中继同步最新消息」；
- 弹窗与「检查更新」共用队列，一次只显示一个（更新优先）。

**同步算法（MVP）**：按会话 LWW

1. 客户端记录 `cursor`（上次拉到的 seq）与每个会话的 `rev`；
2. 启动：`GET changes?since=cursor` → 有变更才进入同步；
3. 拉取：对每个变更 `GET sessions/:id`，与本地 `updatedAt` 比较，服务端更新则替换本地；
4. 推送：本地比服务端新（或服务端没有）→ `PUT sessions/:id` with `baseRev`；
5. 409：说明两端都改过 → 比较 `updatedAt`，新者胜；仍相等则保留本地并生成「冲突副本」会话；
6. 删除：`deleted: true` 的 tombstone 同样按 `updatedAt` 裁决，避免「删除后又复活」；
7. 完成后保存新 `cursor`。

后续可升级为消息级合并（按 message id + 版本），但会话级 LWW 对「一台设备写、其他设备读」的典型场景已经够用。

### 4.6 侧边栏下拉刷新

列表顶部下拉 → 触发一次增量同步 → 完成提示「已是最新 / 同步 n 条」。

## 6. 参考项目分析：dsh-ee

`dsh-ee` 是给企业用的「能力中心」：把 ERP/CRM/知识库接进来，做成微应用下发给员工的 DeepSeek Harness（DSH）。它**不是聊天中继**，但工程结构值得借：

- **Go + 少量依赖 + `go:embed` 内置 WebUI**：单二进制分发，部署简单（我们当前用 Node 换取「无需编译、随时可跑」，后续要单文件分发可平移到 Go）；
- **令牌模型**：`ee_at_` 前缀、能力范围、额度、有效期、设备名、吊销——中继的令牌可以照这个补「设备列表 / 吊销 / 最近使用」；
- **`eejwt`**：只用标准库、固定 RS256、5 分钟短令牌，思路适合以后做「中继之间的互信」；
- **审计**：每次调用留痕（谁、何时、调了什么）。中继下一步也应该在 `proxy` 处落一张调用流水表；
- **`netguard`**：出站地址白名单，避免被当成 SSRF 跳板——我们的代理白名单是同一思路的简化版。

不直接复用的原因：它的领域是「企业连接器 + 权限 + 审批」，我们只需要「转发 + 同步」；直接搬会带进 LDAP、部门、配额等一整套用不上的东西。

## 7. 已知取舍

- **Node 而不是 Go**：当前环境没有 Go 工具链，写了也验证不了；Node 版本已实测通过。要单文件分发时再平移，接口不变。
- **会话级 LWW**：极端并发下可能丢一次编辑，用「冲突副本」兜底；消息级合并留到后面。
- **服务端不解析 payload**：好处是无需跟随客户端字段变化，代价是 WebUI 只能看数量/大小，不能看内容（也正好符合隐私预期）。
